## Problem Statement

开发一个可长期自用、未来可独立开源的 DeepSeek Harness 陪伴插件。它通过现有 `dsh-im` 接入微信或 QQ，以“引导型恋人”的关系姿态陪伴用户：接住分享、引导倾诉、记住长期偏好和未完话题，并在合适的时候主动早安、晚安、推荐内容或发送表情包。

当前 `dsh-im` 已解决扫码接入、会话绑定、模型调用和文件投递，但没有拥有用户画像、关系节奏、主动联系决策和陪伴人格。Harness 自带 Schedule 能触发 Session 后续 Turn，却没有把没有入站消息触发的输出可靠路由回微信或 QQ 的通用边界。

## What Makes This Cool

核心体验不是“机器人定时推送”，而是它会依据两个人真实形成的互动习惯调节亲密程度：

- 用户经常回应时，它可以撒娇、假装生气、连发少量消息或发送表情包。
- 用户经常不回应时，它会逐步降低频率并安静下来。
- 它会记得用户没讲完的事情，并在未来自然回访。
- 它主动分享的互联网内容必须能解释“为什么这可能适合这个用户”，而不是随机资讯流。
- “生气”最终必须收住，不使用内疚、威胁、排他或自我伤害表达迫使用户回应。

## Constraints

- 第一位用户是项目作者本人，聊天、画像和表情包默认只保存在本机。
- 未来可能开源，因此核心逻辑不能绑定单一微信账号、模型或搜索供应商。
- 复用 `dsh-im` 的现有通道与 Harness Session，不重新实现微信、QQ 收发协议。
- 默认每天主动联系 1～3 次，但不是强制凑满；近期正在聊天时取消计划消息。
- 对连续未回复必须确定性降频；模型不能自行突破追发上限。
- 表情包仓库只包含用户自有素材或允许再分发的示例素材，避免版权不清。
- 技术栈与 `dsh-im` 对齐：Node.js 22.19+、ESM、Node Test Runner。

## Premises

1. “生气”是可爱、可收回的角色表达，不是真正惩罚用户。
2. 消息频率、追发上限、静默时段和冷却时间由确定性策略引擎控制。
3. 默认根据长期回复习惯自适应，同时支持温柔、自然、黏人三种互动强度。
4. 连续未回复时逐步降频，不允许无限升级。
5. 聊天、画像和表情包默认本地保存；联网时只提交抽象查询词。
6. 人格文案、记忆提取、话题搜索和渠道投递是不同职责，必须可独立测试和替换。

## Approaches Considered

### Approach A：直接修改 dsh-im

把画像、调度、联网选题和表情包逻辑直接加入 `dsh-im`。原型速度快，但陪伴策略和九个通道耦合，上游同步、测试和独立发布成本高，放弃。

### Approach B：独立 dsh-companion 插件 + 薄通道边界

`dsh-companion` 独立拥有记忆、关系温度、主动调度、话题发现和表情包选择。`dsh-im` 只提供可信会话路由、入站活动通知和主动发送消息的能力。该方案已经由用户确认。

### Approach C：独立 Companion Server

使用单独进程通过 HTTP/WebSocket 控制 IM。扩展空间大，但需要新增认证、队列、部署和进程治理，对第一版过重，放弃。

## Recommended Approach

采用 Approach B，并分为可独立验证的两层：

```text
微信 / QQ
    │
    ▼
dsh-im 通道适配器
    │  入站活动 / 主动投递
    ▼
companion-channel seam
    │
    ├── 关系节奏策略
    ├── 本地长期记忆
    ├── 主动联系调度
    ├── 联网话题发现
    ├── 表情包选择
    └── 陪伴 Session / Agent Preset
```

第一阶段先完成与渠道无关的 `dsh-companion` 核心、内存测试适配器和 WeChat 参考适配接口。实际 `dsh-im` 补丁保持很薄：不理解陪伴策略，只注册可主动投递的私人路由并上报入站事件。

## Public Contracts

### Terms

- **Candidate**：某个时间窗口产生的待评估机会，尚未占用每日预算。
- **Plan**：通过策略检查后持久化的一次主动联系，可包含 1～3 条子消息。
- **Message**：一个独立投递单元，即一个文字气泡或一个表情包。
- **Follow-up**：在上一 Plan 后尚无用户入站时创建的新 Plan；同一 Plan 内的多气泡不算 Follow-up。
- **Reply**：某个 Plan 最后一条已确认发送消息之后、下一次主动 Plan 之前收到的第一条用户入站消息。
- **Cancelled**：原本合法的 Plan 因用户回复、暂停、路由撤销或配置变化而失效。
- **Skipped**：Candidate 在形成 Plan 前未通过策略检查，因此从未进入可执行状态。

### Companion route

```ts
interface CompanionRoute {
  routeId: string
  channel: 'weixin' | 'qq' | string
  botId: string
  conversationId: string
  kind: 'direct'
  ownerId: string
  sessionId?: string
  lastInboundAt?: string
  routeVersion: number
  inboundVersion: number
}
```

第一版只允许 `kind: 'direct'` 的已验证所有者私聊进入主动联系系统，不向群聊主动发送。

### Outbound message plan

```ts
interface CompanionMessagePlan {
  planId: string
  routeId: string
  reason: 'morning' | 'evening' | 'topic' | 'follow-up'
  messages: Array<{
    kind: 'text' | 'sticker'
    text?: string
    stickerId?: string
    delayMs: number
  }>
  expiresAt: string
}
```

策略引擎先限定消息数量和延迟，模型只能填写被允许的消息槽位。投递器必须在每条发送前重新检查计划是否过期、用户是否刚刚回复以及是否进入静默时段。

### Channel adapter

```ts
interface CompanionChannelAdapter {
  channel: string
  capabilities(route: CompanionRoute): Promise<{
    text: boolean
    image: boolean
    idempotency: 'provider' | 'local-at-most-once'
  }>
  health(route: CompanionRoute): Promise<'online' | 'offline' | 'unknown'>
  send(route: CompanionRoute, message: CompanionOutboundMessage, options: {

```

适配器返回明确的成功、拒绝、限流或不确定状态；不确定状态禁止自动重发，避免重复消息。

### dsh-im gateway seam

`dsh-im` 暴露一个带项目命名空间的平台无关只读消费服务 `ctx.dshImGateway`。它只拥有渠道身份与投递，不依赖陪伴插件：

```ts
interface DshImGateway {
  getRoute(routeId: string): Promise<CompanionRoute | null>
  getCapabilities(routeId: string): Promise<ChannelCapabilities>
  getHealth(routeId: string): Promise<ChannelHealth>
  send(routeId: string, message: CompanionOutboundMessage, options: {
    idempotencyKey: string
    signal?: AbortSignal
  }): Promise<DeliveryReceipt>
  onInbound(listener: (event: ImInboundEvent) => void): () => void
  onRouteChanged(listener: (event: ImRouteEvent) => void): () => void
  readInboundSince(cursor: string | null, limit: number): Promise<{
    events: ImInboundMetadata[]
    nextCursor: string | null
  }>
}
```

路由写入面是 dsh-im 内部的 `ImGatewayRegistry`，不注册到公共 Cordis Context，其他插件无法伪造 `RouteProof` 或创建路由。路由只能由 dsh-im 在成功处理已验证所有者私聊时创建或刷新。`routeId` 由 `channel + botId + kind + conversationId` 的规范化值生成，升级和重启后保持稳定。凭据失效、机器人移除、owner 改变或会话被平台撤销时由 registry 撤销路由。

```ts
interface RouteProof {
  kind: 'configured-owner' | 'qr-bound-owner'
  ownerId: string
  botCredentialId: string
  verifiedAt: string
}

interface ImInboundEvent {
  cursor: string
  routeId: string
  messageId: string
  occurredAt: string
  routeVersion: number
  inboundVersion: number
  normalizedText?: string // 只在进程内实时事件中存在，不写 gateway journal
  controlIntent?: 'pause_proactive' | 'resume_proactive'
}

interface ImInboundMetadata extends Omit<ImInboundEvent, 'normalizedText'> {}
```

每条合法入站先在 dsh-im 的 route journal 中事务性增加单调 `inboundVersion`，再进入 Harness 和进程内 listener。只有精确匹配注册命令的 `pause_proactive/resume_proactive` 会作为 `controlIntent` 写入 journal，聊天正文不持久化。Companion 启动时从持久 cursor 补读 metadata 并重放控制意图；发送前始终调用 `getRoute()` 比较 gateway 当前 `routeVersion/inboundVersion`，因此即使实时回调丢失，也会取消基于旧版本生成的剩余消息。

gateway journal 默认保留 90 天。Companion 持久保存消费 cursor；若 cursor 已过期，插件进入 `inactive-needs-resync`，从 gateway 获取所有 route 的当前版本并要求操作者确认 proactive 状态后才恢复发送，禁止在历史控制意图未知时自动继续。

## Plugin Lifecycle

1. `dsh-companion` 加载后打开 SQLite、执行迁移并注册 `ctx.companion` 服务。
2. 它等待 `ctx.dshImGateway` 可用，订阅入站与路由变更事件；没有 gateway 时保持可诊断的 inactive 状态，不启动发送 worker。
3. 启动时从已保存 cursor 补读入站 metadata 并刷新 route 版本，再处理过期 lease：`claimed` 且没有 attempt 时可回到 `planned`；`sending` 或消息级 `sending` 一律转为 `delivery_unknown`，绝不盲目重发。
4. 单个 worker 每次在 `BEGIN IMMEDIATE` 事务内完成“重新检查策略、领取 Plan、写入 lease”；外部 IM 调用在事务外执行。
5. 每条消息发送前再次比较 route version、owner control version 和最近 inbound version。发生变化则取消尚未发送的子消息。
6. Host 关闭时停止领取新 Plan、取消可取消的网络调用、等待当前数据库提交完成并释放资源。
7. 内容生成通过一个专用 Companion Session 进行。调度器传入最小必要画像投影与候选原因，模型返回结构化内容槽位；策略层验证后才写入 `plan_messages`。

## Delivery State Machine

| 当前状态 | 触发 | 下一状态 | 恢复/重试规则 |
|---|---|---|---|
| planned | worker 成功领取 lease | claimed | lease 过期且没有发送尝试时可重新领取 |
| planned | 过期 | expired | 终态，不补发 |
| planned/claimed | 暂停、入站回复、路由撤销 | cancelled | 终态 |
| claimed | 开始首条投递 | sending | 写入消息级 attempt 后才调用渠道 |
| sending | 全部子消息确认成功 | sent | 终态 |
| sending | 渠道明确永久拒绝 | failed_final | 终态 |
| sending | 超时、连接断开、结果不确定 | delivery_unknown | 终态，人工确认前不重发 |
| sending | 用户在气泡间回复 | sending | 已发消息保留，剩余 pending 消息改 cancelled，随后 Plan 改 sent |
| sending | 明确 rate limit 且允许一次延期 | planned | 设置 `retry_scheduled_at=now+retryAfter`、`retry_count=1`，清空 lease；第二次限流转 failed_final |

外部 IM 调用无法与 SQLite 事务原子提交。若渠道支持幂等键则把 `message.idempotencyKey` 传给渠道；不支持时采用本地 at-most-once：attempt 一旦写入且调用开始，崩溃恢复后标记 unknown，不自动重发。这样可能少发一次，但不会骚扰性重复发送。

计划状态与适配器结果映射：

| 适配器结果 | 消息状态 | Plan 处理 |
|---|---|---|
| sent | sent | 继续下一条 |
| rejected/permanent | failed_final | Plan failed_final，取消剩余消息 |
| rate_limited 且仍在 expiresAt 前 | pending | 释放 lease，按明确 retryAfter 延迟一次 |
| rate_limited 且将过期 | failed_final | 不延期到错误时段 |
| timeout/unknown | delivery_unknown | Plan delivery_unknown，禁止自动重试 |
| route revoked/offline | cancelled | 取消剩余消息 |

## Relationship Temperature

关系温度不是让模型输出一个主观分数，而是由最近 30 天事件通过固定公式计算。所有样本按 7 天半衰期指数衰减；没有样本的指标使用 0.5 中性值：

- `replyRate`：主动 Plan 在 6 小时内且下一 Plan 前获得回复的衰减加权比例。
- `initiationRate`：30 天窗口内、按 7 天半衰期加权的“用户主动开启聊天日”占有互动观察日的比例。
- `replySpeed`：每个已回复 Plan 的 `max(0, 1 - latency / 6h)` 衰减加权均值。
- `ignorePenalty`：`min(consecutiveUnansweredPlans / 3, 1)`。

```text
base = 0.35*replyRate
     + 0.25*initiationRate
     + 0.20*replySpeed
     + 0.20*(1-ignorePenalty)

temperature = clamp(base + explicitFeedbackAdjustment, 0, 1)
```

`initiationRate` 同样使用 30 天窗口与 7 天半衰期，分母是观察窗口内有任何互动的衰减加权天，分子是包含用户主动开启聊天的天；分母为零时取 0.5。其他指标没有有效样本时也取 0.5。

最近 30 天只采用时间上最新的一条显式反馈：正反馈调整 `+0.15`，负反馈调整 `-0.30`，超过 30 天自动失效，因此正负反馈不会叠加。明确“别催我/停止主动”不参与分数，直接触发 owner control paused。

`consecutiveUnansweredPlans` 只统计至少有一条子消息明确 sent、且最后一条已发送消息后 6 小时内没有 Reply 的 Plan。cancelled、failed_final、delivery_unknown 不进入序列；部分发送后其余消息被取消的 Plan 仍以最后一条已确认消息为起点判断。

输出状态：

| 状态 | 典型条件 | 主动行为 |
|---|---|---|
| quiet | `temperature < 0.35` 或连续 3 次未回复 | 24～72 小时冷却，每天最多 1 次，不追发 |
| normal | `0.35 <= temperature < 0.70`，且连续未回复少于 3 次 | 每天 1～2 次，不超过 1 次轻追发 |
| warm | `temperature >= 0.70`，且连续未回复不超过 1 次 | 每天最多 3 次，偶尔允许 2～3 条拟人化连发 |

无论状态如何，都设置不可突破的硬限制：

- 单次主动计划最多 3 条消息。
- 未收到新回复前最多执行 1 个追发计划。
- 每日默认最多 3 个主动计划。
- 静默时段不发送，除非用户主动开启聊天。
- 出现 `停止主动消息`、`别催我` 等明确意图时立即暂停，直到用户重新开启。

### Interaction mode policy

| 模式 | 普通日预算 | 同一 Plan 最大气泡 | Follow-up | 最短主动间隔 |
|---|---:|---:|---|---:|
| gentle | 1 | 1 | 禁止 | 12 小时 |
| natural | 2，warm 时可到 3 | normal 1，warm 3 | 仅 warm，最多 1 次 | 4 小时 |
| clingy | 3 | normal 2，warm 3 | normal/warm 最多 1 次 | 2 小时 |

quiet 状态覆盖模式配置：每天最多 1 次、禁止 Follow-up。冷却按未回复 streak 确定：3 次为 24 小时、4 次为 48 小时、5 次及以上为 72 小时。

Follow-up Candidate 仅在上一 Plan 至少一条 sent、尚未收到 Reply、当日预算仍有余额时生成。natural 的等待时间为 `clamp(1.5 × 最近30天回复延迟中位数, 45分钟, 3小时)`；没有历史时为 90 分钟。clingy 为 `clamp(回复延迟中位数, 20分钟, 90分钟)`；没有历史时为 45 分钟。若下一 Morning/Topic/Evening 候选在 2 小时内，则不生成 Follow-up，避免窗口冲突。

## Proactive Scheduling

调度器拥有自己的持久记录和恢复逻辑，不依赖一个始终保持热状态的 Harness Session。

每天生成候选窗口：

- Morning：用户本地时间 07:00～10:30。
- Topic：11:00～20:30 内随机，但避开最近聊天后的冷却期。
- Evening：21:00～23:59。

候选随机使用 `ownerId + localDate + windowKind` 的稳定哈希作为种子，并写入 `proactive_candidates`；唯一约束保证同一天同一窗口只产生一个 Candidate/Plan。用户更改时区后，只重算 status=pending 的 Candidate。跨午夜静默区间按用户本地时区判断；不存在的夏令时时刻顺延到第一个有效时刻，重复时刻只执行一次。

`expiresAt` 为窗口结束与计划创建后 90 分钟二者中的较早值。Host 离线时保留 planned，恢复时仅执行仍未过期且重新检查全部条件通过的 Plan；过期直接标记 expired，不发送“补早安”。

每个候选执行前依次检查：

1. Host 与目标渠道是否在线。
2. 路由是否仍属于已验证所有者私聊。
3. 是否处于静默时段或暂停状态。
4. 最近是否已发生入站聊天。
5. 当日预算是否用完。
6. 连续未回复是否要求降频。
7. 当前候选是否有足够具体的发送理由。

Candidate 检查失败记录可解释的 `skipped` 原因，不调用模型。已经持久化的 Plan 因新入站、暂停、配置变化或路由撤销失效时记录 `cancelled`。

暂停命令使用两层识别：确定性规范化命令（`/companion pause`、`停止主动消息`、`别再催我`）立即生效；自然语言分类器只能提出暂停建议，需在回复中确认，防止把普通抱怨误判为永久暂停。恢复必须由 `/companion resume` 或明确同义表达触发，并跨重启保持。

## Topic Discovery

主动联网搜索分成规划和获取两步：

1. 从低敏感度兴趣、最近公开话题和未完问题生成抽象查询，不包含原始聊天全文、人名、地址或高度私密记忆。
2. 使用 Harness `web_search` 获取候选内容，必要时用 `web_fetch` 读取原文。
3. 以兴趣匹配、时效、来源质量、是否重复和是否真的能开启对话评分。
4. 低于阈值时放弃发送，不为了完成每日次数而发送弱内容。
5. 保存 URL、标题、检索时间和“为什么匹配”的解释，避免几天内重复推荐。

聊天中的联网搜索不受主动话题预算限制，但仍遵守隐私查询重写和来源引用规则。

## Sticker Routing

表情包由本地清单管理。模型输出语义意图，不输出文件路径：

```ts
interface StickerIntent {
  emotion: 'happy' | 'sad' | 'angry_playful' | 'comfort' | 'surprised' | 'teasing'
  intensity: 1 | 2 | 3
  context: 'reply' | 'follow-up' | 'morning' | 'evening'
}
```

选择器根据标签、强度、冷却时间、最近使用记录和渠道能力选择 `stickerId`，随后解析为受信本地文件。找不到合适素材时退化为文字，不生成无关图片。

## Human Voice Contract

每次回复先选择行为，再生成措辞：

1. 判断用户此刻主要是在分享、倾诉、求建议、开玩笑还是需要空间。
2. 选择 `陪着听 | 轻追问 | 共鸣分享 | 提供建议 | 玩笑撒娇 | 简短回应`。
3. 默认只提出一个问题；不是每轮都必须提问。
4. 移动端回复默认 1～3 个短消息气泡，不输出咨询报告式长文。
5. 避免重复“我理解你”“听起来你……”等模板开头。
6. 允许形成稳定口头习惯，但必须有频率约束，不能每次复读角色口癖。

## Privacy and Safety

- 默认不遥测、不上传数据库、不收集匿名聊天样本。
- 提供画像查看、单条删除、全部清除、导出和暂停记忆能力。
- 日志默认不记录消息正文、搜索查询原文或表情包绝对路径。
- 对高度私密记忆默认禁止用于互联网查询。
- 开源示例不得包含真实用户对话、私人画像或版权不明表情包。
- 角色可以撒娇或假装生气，但禁止威胁离开、自伤、贬低用户、制造排他关系或将回复义务道德化。

### Data flow matrix

| 数据 | 本地 SQLite | 聊天模型提供商 | 搜索提供商 | 默认日志 |
|---|---:|---:|---:|---:|
| 原始聊天正文 | Harness Session 持有；companion 不复制 | 当前会话需要时会发送 | 禁止 | 禁止 |
| 低敏感度画像摘要 | 是 | 仅最小必要投影 | 只发送抽象查询词 | 仅 memoryId |
| private/highly_private 记忆 | 是 | 当前倾诉上下文需要时可发送 | 禁止 | 禁止 |
| 搜索查询 | URL/查询哈希与安全摘要 | 规划时可见 | 是 | 仅哈希 |
| 表情包绝对路径 | 是 | 禁止，模型只见 stickerId/标签 | 禁止 | 仅 stickerId |
| 投递错误 | 安全错误码 | 否 | 否 | 安全错误码 |

第一版提供 CLI：`companion profile show`、`memory list/forget/erase/clear/export/pause/resume`、`proactive pause/resume/status`。

- `forget`：将记忆标为 forgotten、重建画像投影并清理未执行 Plan 的相关内容快照；保留最小 tombstone 供审计，但后续提示词不得引用。
- `erase`：物理删除指定记忆、投影、未执行内容快照和关联 topic source；数据库备份不会被静默改写，命令必须列出仍可能含旧数据的备份并提供显式删除路径。
- `clear`：执行 owner 范围物理删除，但不自动删除 Harness Session；CLI 必须明确展示 Harness Session 是另一数据所有者，并给出相应 Session 删除/归档指引。
- 已经发送到微信/QQ或外部模型/搜索提供商的数据无法由本地删除撤回，CLI 在确认前必须说明该边界。

## Success Criteria

1. 单元测试证明关系温度在高回复、普通和连续未回复三类事件序列下得到稳定、可解释的状态。
2. 连续 3 次主动消息未回复后，系统进入 quiet，且未回复前不会执行追发计划。
3. warm 状态允许一次最多 3 条的拟人化计划，但硬上限不可由模型输出突破。
4. 暂停事务提交后不得开始任何新消息；若正在两个气泡之间，所有剩余消息立即取消。
5. 重启后只有 planned 和没有 attempt 的过期 claimed 可恢复；sending 转为 delivery_unknown，已过期计划不会补发。
6. 联网查询重写测试证明私密字段、人名和原始聊天段落不会进入查询。
7. 表情包选择遵守标签、强度和冷却时间；素材缺失时安全退化为文字。
8. 内存渠道端到端测试能完成：入站聊天 → 更新互动事件 → 生成主动候选 → 策略批准 → 发送多气泡/表情包 → 记录回执。
9. WeChat 参考适配器只向已验证所有者私聊发送，群聊和未知路由被拒绝。
10. `npm test` 与 `npm run check` 全部通过，核心模块保持无平台依赖。
11. 发送第一个气泡后模拟进程崩溃，重启后不重复第一个气泡，Plan 进入 delivery_unknown。
12. 渠道返回超时或 unknown 时不自动重试。
13. 两个 worker 同时领取同一个 Plan 时只有一个成功获得 lease。
14. 用户在多气泡之间回复时，尚未发送的气泡全部取消。
15. paused、route revoked 和 owner 验证失效跨重启保持并阻止投递。
16. 覆盖跨午夜静默时段、时区变更及夏令时跳跃/重复边界。
17. 日志和错误输出中不出现聊天正文、原始查询或绝对文件路径。
18. 删除一条记忆后，画像投影和未来提示词均不再引用它。
19. 固定事件 fixture 对关系温度给出精确数值和状态断言。
20. 丢弃实时 inbound 回调后，worker 仍能通过 gateway 当前 inboundVersion 发现用户已经回复并取消发送。
21. 同一 owner/date/window 在并发候选生成时只形成一个 Candidate 和一个 Plan。
22. natural、gentle、clingy 的预算、气泡数、Follow-up 和最短间隔均有确定性测试。
23. rate limit 只允许一次延期，状态从 sending 回到 planned；第二次限流进入 failed_final。
24. `forget` 停止未来引用，`erase` 物理删除 companion 数据并明确报告仍存在的外部/Harness/备份边界。
25. Companion 停机期间用户发送精确暂停命令，恢复并 replay journal 后仍保持 paused；cursor 失效时进入 needs_resync 且禁止发送。
